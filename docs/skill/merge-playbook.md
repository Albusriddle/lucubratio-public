# 合稿手册（Lead 专用）

## 一、分工：谁决定什么

| 归 reviewer（必须写成可执行替换） | 归 Lead（结构决策，reviewer 只给建议） |
|---|---|
| 事实性错误、遗漏、编造 | 用哪份稿做骨架 |
| 表述取舍（A 的说法 vs B 的说法） | 每段并进哪几块（如"用 A 的练习汇总表"） |
| 检测题的改写、换项、改解析 | 最终题集如何组合（跨段去重、考点覆盖） |
| 输出的形式：`PATCH n / 文件 / 原文 / 改为 / 理由` | 全页题量是否超上限、要不要再删 |

**为什么**：合稿决策依赖**全局信息**（全页题量上限、跨段重复考点、整体章节结构），
reviewer 只看一段时看不到这些。让它决定会出错，让它"给建议"才对。

## 二、合稿决策模板（每段填一遍，留档）

```
段 N（p X–Y）：
  骨架 = A / B       理由：
  并入 = A 的「__」、B 的「__」
  舍弃 = A 的「__」（理由：重复 / 记忆化 / 同页同考点）
  题集 = 保留 __，删除 __（去重依据：__）
  待人工核对 = __（reviewer 标了「无法核实」的条目）
```

## 三、执行顺序（不可颠倒）

1. **先按「文件」拆 PATCH**，再分别应用
   ```bash
   node tools/apply-patches.mjs review-sN.md <目标片段> --as A
   node tools/apply-patches.mjs review-sN.md <目标片段> --as B
   ```
   工具会在补丁里的「文件：」与 `--as` 不符时给出明确提示（而不是整批失败）。
2. **跨文件搬块**用 `IMPORT`（见下），不要手工复制粘贴
3. 合稿后先跑 `tools/lint-fragment.mjs`
4. 多段合并用 `tools/merge-pages.mjs`（自动重编号 + 查 id 唯一性 + 查全页题量上限 + 查元叙述残留）
5. `build → verify → pack → verify-package`
6. 装机：真导入、真打开、滚到图看渲染

## 四、IMPORT：跨文件搬块

当 reviewer 说「用 A 的检测 5 替换 B 的检测 5」时，别手工复制，写成：

```
IMPORT 1
文件：A
取：<h3 id="检测 5">
到：<h3 id="检测 6">
替换：<h3 id="检测 5">
```

- `取`/`到` 用**标记**定位（不是行号），对格式变化更稳
- 搬进来的块会自动改 id 前缀，避免与目标文件冲突
- 与 PATCH 同一事务：任一条失败则整批不写入

## 五、合稿后必须自查的四件事

| 检查 | 命令/方法 |
|---|---|
| 元叙述残留（"这一稿""本稿"） | `merge-pages` 已内置 |
| 章节 id 全局唯一 | `merge-pages` 已内置 |
| 全页题量 ≤ 上限（≤20 页 8 / 20–60 页 10 / 60+ 页 12） | `merge-pages` 已内置 |
| 题目本身可答（答案/解析/选项三者自洽） | `node tools/self-check-quizzes.mjs <页面>` |

## 六、别做的事

- 别在合稿时"顺手补一句"——任何新增内容都要能指到页码，否则就是编造
- 别因为"两稿都不错"就都保留：同一考点出两题，等于稀释
- 别相信 producer 自述作为线索（见 `SKILL.md` 的「线索自验」）
